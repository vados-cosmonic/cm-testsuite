# Contribution conventions

Read only the sections relevant to the current task.
These conventions describe how to prepare a contribution; they do not authorize creating a PR or publishing changes.

## Commits

- Work on a feature branch, never directly on `main`.
- Write titles as `type(scope): description`, for example `fix(delivery): preserve excluded tests`.
  Only the types and scopes listed in [commitlint.config.mjs](../../../commitlint.config.mjs) pass CI.
  The scope is optional; omit it when none of the listed ones fits.
- Keep body and footer lines within 100 characters.
- Sign off every commit with `git commit -s`.
- Keep commits small and organized around semantically distinct changes.
- Mark a breaking change with `!` in the title and a `BREAKING CHANGE:` footer.
- The `release` type is reserved for commits generated by the release workflow.
- Rebase onto `main` instead of merging `main` into a branch.
- To lint the proposed range, run `npm ci --ignore-scripts` once (Node.js 24 or newer), then
  `dotslash bins/just xtask lint-commits --from origin/main --to HEAD`.

## Pull requests

- CI lints the PR title as well, because it may become a squash commit.
  Give it the same Conventional Commit form.
- Explain the behavior changed, why it matters, and the checks you ran.
- Open a pull request as a draft after local checks pass.
- Say which checks could not run and why.
- Do not commit build output, `.llm/` notes, `.buckroot`, `.buckconfig.local`, or credentials.
- Do not edit `CHANGELOG.md`; git-cliff generates it from commit titles during release preparation.

## Documentation

- Write for users and maintainers, and describe actual behavior rather than plans.
- User and contributor documentation lives in the mdBook under `docs/src/`;
  add new pages to `docs/src/SUMMARY.md`.
  Operational maintainer procedures belong in [MAINTAINERS.md](../../../MAINTAINERS.md).
- Use GitHub-compatible admonitions for warnings and tables for pinned versions.
- Update documentation in the same change as the behavior, paths, or commands it describes.
- Record adapted third-party material in [THIRD_PARTY.md](../../../THIRD_PARTY.md).
- Verify documentation changes with `dotslash bins/just site`.
- In `AGENTS.md` and these skills, state only what an agent cannot learn from the code,
  link to the existing documentation instead of repeating it,
  and use [semantic line breaks](https://sembr.org).
